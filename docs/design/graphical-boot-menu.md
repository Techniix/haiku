# Graphical boot menu (F-22, batch B): design note

Status: proposal for the architect's review before any change under `src/system/boot/` (a protected
path). It turns the roadmap's approved plan (F-22, "Boot loader review, 2026-11-12", batch B) into a
structure, an order of work and tests. Nothing here changes the text menu's behaviour.

## Goals and limits (from the roadmap)

- Renga theme only: no logo, dark background, light shifting over the items like leaves overhead,
  a few leaves drifting; drawn procedurally so it scales to any resolution.
- No mode switch: the firmware's current mode (UEFI GOP, or the VESA mode the BIOS loader already
  sets for the splash) is used, and the menu fades straight into the boot splash.
- A frame-time budget: when frames are slow the animation stops on a still frame; when there is no
  usable framebuffer the text menu runs exactly as today. A setting turns the animation off.
- Keyboard first; any key pauses the countdown; F1 opens a help screen listing every key.
- Boot options chosen from a per-entry options panel (safe mode, native drivers only, roll back,
  collect diagnostics, debug output, screen resolution, disable SMP/ACPI ...), with shortcut keys.
- System info screen (CPU, memory, graphics, disks, firmware, Secure Boot; drivers from the last
  boot, labelled as such).
- Localised strings from build-time tables; Lato glyph atlases at several sizes; icons rendered from
  HVIF at build time.

## Structure

The menu model stays in `src/system/boot/loader/menu.cpp` (`Menu`, `MenuItem`, the entries for other
systems, restore points, safe-mode options). Only the presentation changes:

1. `platform_run_menu()` (EFI `src/system/boot/platform/efi/menu.cpp`, BIOS
   `bios_ia32/menu.cpp`) calls a new `platform_generic_run_graphical_menu(menu)` first. It returns
   `B_UNSUPPORTED` when there is no linear framebuffer of 24/32 bits, when the
   `boot_menu_graphics false` setting is present, or when the first frame misses its budget. The
   caller then falls back to `platform_generic_run_text_menu()`. The fallback is decided before
   anything is drawn, so a failure never leaves half a screen.
2. New files under `src/system/boot/platform/generic/` (shared by EFI and BIOS):
   - `graphical_menu.cpp`: layout (list of entries with icon, name and hint line; countdown; key
     bar), input loop (the same key handling as `text_menu.cpp`: arrows, Enter, Escape, digits 1-9 for
     other systems, letters for the shortcut keys) and screens (main list, options panel, help, system
     info).
   - `boot_canvas.cpp`: a small software renderer on the framebuffer, with a back buffer in loader
     heap memory (one full frame; at 4K that is 33 MB, so above 2560x1600 the light effect runs at
     half resolution and is scaled up), rectangles, alpha blits, a glyph-atlas text renderer and
     present-with-dirty-rectangles.
   - `boot_light.cpp`: the procedural light. A few value-noise layers at low resolution (one sample
     per 8x8 block), scrolled slowly in two directions, plus three to six leaf sprites on Bezier
     paths. A fixed time step is used, and frame times are measured with `system_time()`.
3. Build-time assets (`src/system/boot/platform/generic/assets/`, generated by a host tool under
   `src/tools/`): Lato atlases at 16, 24, 32 and 48 px (ASCII plus the characters the translations
   need), and icons for Renga/Haiku, Windows, Linux (generic and a few distributions by name), BSD,
   macOS, removable media and restore points, at 32, 48 and 64 px, from HVIF. The loader picks the
   size from the screen height.
4. Strings come from a generated table keyed by a language code. Where the code comes from (a new
   field in the loader state `/boot/system/settings/boot/state`, or the Locale settings read from the
   boot volume) is still open for review. English is the fallback.

The loader must stay small (the BIOS loader's size has to be checked). The plan is to keep the assets in a
separate file the loader reads from the boot volume when the graphical menu starts (`boot_menu.rsrc`
next to the kernel). If the file is missing, the text menu runs. Only the renderer code goes into the
loader binary. The budget is about 40 KiB of code, which must be checked against the BIOS loader's
limit before the first commit.

## Settings and GUI

Boot menu preferences (`src/preferences/bootmenu`, not protected) gain a "Graphical menu" switch
(on), an "Animation" switch (on), and later the per-entry rename, hide, reorder and icon choice. They
are written as `boot_menu_graphics` and `boot_menu_animation` lines in the kernel settings file the
loader already reads for the timeout and default.

## Order of work (each step its own commit, each protected change with the architect's approval)

1. Canvas, fallback and a static list (no animation, no options): EFI only, behind the switch, off by
   default until its tests pass. Tests: QEMU screenshots on UEFI at 1024x768 and 1920x1080 (the
   harness's `bootmenu` suite gains `--firmware uefi` screenshot checks of the boot menu), plus a
   fallback check with the switch off (the text menu screenshot is unchanged).
2. BIOS (VESA) on the same code; the screenshot checks on BIOS.
3. Light and leaves with the frame budget; a check that frames are dropped to a still image under a
   forced slow budget (a harness-only setting).
4. Options panel, help screen, shortcut keys; key-driven checks through the harness's sendkey.
5. System info screen and the last boot's driver list (from the boot progress record, F-67).
6. Localisation tables and the Boot menu preferences' customisation.

Each step runs the `bootmenu` and `bootstate` suites and one default-profile boot run. The full
four-way sweep runs at the end of the batch, as for all boot-path changes. Hardware Tested only on the
maintainer's PC.

## Risks

- Slow framebuffers (some GOP implementations are uncached): handled by the measured budget and the
  still-frame fallback; the first frame is drawn before the countdown starts.
- Loader size on BIOS: assets stay outside the binary, as above.
- Input: the existing key handling and its QEMU quirks (the first PS/2 key is lost on the WSL host)
  stay the same, because the graphical menu uses the same input functions.
